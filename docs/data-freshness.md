# 账户数据新鲜度：现状、根因与已实施方案

> 适用版本：v2.4.0+（阈值分级）／v2.5.0+（自调度链路）
> 相关文件：`.github/workflows/sync-data.yml`、`src/config.js`、`src/app.js`、`src/render.js`

> **状态：方案 A 已实施（v2.5.0）** —— 采用 GitHub 原生自调度链，**不需要**外部定时服务、**不需要**额外 PAT。
> 效果：数据每 10 分钟刷新一次；链路意外中断后最多 **30 分钟**由兜底 `schedule` 自愈。

## 1. 现状

账户事实（持仓、均价、克重、网格参数）来自私有库 `git202526/xau-desk-data`，前端无法直连（仓库私有、需令牌），只能由 GitHub Actions 定时同步为公开快照 `data/live.json` + `data/meta.json`。

`meta.json` 记录最近一次同步时间：

```json
{ "syncedAt": "2026-11-12T19:12:59.711Z", "sourceUpdatedAt": 1794497393074, "mode": "actions" }
```

## 2. 根因：GitHub scheduled workflow 会被大幅延迟

工作流原本配置 `cron: "*/15 * * * *"`，但实际运行间隔常达 **4–8 小时**。这不是配置写错，而是 GitHub 对 scheduled workflow 的既有行为：

- 高峰期排队，可能延迟数小时甚至跳过；
- 仓库活跃度低时优先级更低；
- 官方文档明确说明 schedule 不保证准时。

因此「页面显示数据陈旧」并非前端 bug，而是同步链路本身的时效上限。

## 3. v2.4.0 已做的改进（无需额外配置）

| 改进 | 说明 |
|---|---|
| cron `*/15` → `*/5` | 提高触发命中率；GitHub 最小间隔为 5 分钟，仍可能延迟 |
| 阈值分离 | 行情用 `staleMinutes=15`（严格），账户快照用 `accountStaleMinutes=360`（宽松），避免把正常调度延迟误报成「陈旧」 |
| 页脚分级 | 「账户快照 3.2 小时前」按分钟 / 小时显示，超过 6 小时才标「（陈旧）」 |
| `push` 顺带同步 | 每次发版 push 到 `main` 也会触发一次同步，不完全依赖 schedule |

## 4. 已实施：GitHub 原生自调度链（v2.5.0，方案 A 的实现）

`workflow_dispatch` 是即时触发的，不受 schedule 排队影响。既然 GitHub 自带的 `GITHUB_TOKEN` 支持 `workflow_dispatch`（属于官方文档列明的「不会被 GITHUB_TOKEN 抑制」的例外事件），就让**工作流自己在轮末调度下一轮**，不需要任何外部 cron、也不需要长期 PAT。

### 4.1 链路结构

```
run(N) ── 同步 ×6 轮（每 10 分钟一次，约 60 分钟）
        └─ 轮末：gh workflow run sync-data.yml --ref main
                                  ↓
run(N+1) ── 同上 …… 持续滚动
```

| 参数 | 值 | 理由 |
|---|---|---|
| `SYNC_INTERVAL` | `600`（10 分钟） | 每小时 6 次 Pages 构建，低于免费站点 10 次/小时软限制；对网格决策已足够 |
| `SYNC_ROUNDS` | `6` | 单次 run 约 60 分钟，避免长时间占用 runner |
| `timeout-minutes` | `75` | 兜住异常挂起 |
| 兜底 `schedule` | `*/30 * * * *` | 链断了最多 30 分钟自愈 |
| 权限 | `contents: write` + `actions: write` | 仅仓库内置令牌，无外部凭证 |

### 4.2 防双链与自我修复

- **只在 `schedule` / `workflow_dispatch` 触发的 run 里自调度**；`push`（发版）触发的 run 只同步一次，不接链。
- dispatch 前先查 `--status=queued` 与 `--status=in_progress`，排除自身 `GITHUB_RUN_ID`；已有其他任务在跑/排队则**跳过自调度**。
- 单轮抓取失败只打印日志并保留上一份快照（`|| echo`），不会中断整条链。
- 推送前 `git pull --rebase --autostash`，失败重试 3 次，避免与并发提交分叉。

### 4.3 熔断与回滚

- 停止链路：仓库 Settings → Variables 设 `SYNC_LOOP=off`，或在 Actions 页面 Disable workflow。当前 run 会把尾巴跑完，之后不再自调度。
- 回滚到 v2.4.0 行为：`git checkout v2.4.0 -- .github/workflows/sync-data.yml`，即回到纯 `schedule` 模式（会重新变慢）。
- 想改刷新频率：只改 `SYNC_INTERVAL`（秒）。低于 600 会逼近 Pages 构建软限制，不建议。

### 4.4 如何确认链路活着

```bash
gh run list --workflow=sync-data.yml --limit 10 \
  --json createdAt,event,status,conclusion \
  --jq '.[] | "\(.createdAt) \(.event) \(.status)/\(.conclusion)"'
```

健康特征：`event` 交替出现 `workflow_dispatch`，相邻 run 的 `createdAt` 间隔约 60 分钟；页面页脚「源数据 / 账户快照」应为个位数到十几分钟。

## 4A. 备选：外部定时器触发 `workflow_dispatch`（本方案未采用）

若将来想彻底摆脱 GitHub Actions 的链路（例如换成自己的服务器），仍可用外部 cron 触发，此时需要一把只授 `Actions: Read and write` 的细粒度令牌：

```bash
curl -X POST \
  -H "Authorization: Bearer $GH_TOKEN" \
  -H "Accept: application/vnd.github+json" \
  -H "Content-Type: application/json" \
  https://api.github.com/repos/git202526/xau-copilot/actions/workflows/sync-data.yml/dispatches \
  -d '{"ref":"main"}'
```

Cloudflare Worker 版本（`[triggers] crons = ["*/5 * * * *"]`，令牌放 Worker Secret）：

```js
export default {
  async scheduled(event, env) {
    await fetch(
      "https://api.github.com/repos/git202526/xau-copilot/actions/workflows/sync-data.yml/dispatches",
      {
        method: "POST",
        headers: {
          Authorization: `Bearer ${env.GH_TOKEN}`,
          Accept: "application/vnd.github+json",
          "Content-Type": "application/json",
          "User-Agent": "xau-copilot-cron",
        },
        body: JSON.stringify({ ref: "main" }),
      }
    );
  },
};
```

> 令牌只存在外部服务端，**绝不写入前端或仓库**。当前 v2.5.0 的自调度链不需要这一步。

## 5. 根治方案 B：老应用仓库转公开 + 前端直连（时效最好，需权衡隐私）

若把 `xau-desk-data` 设为 public，前端可直接 `fetch`：

```js
const raw = "https://raw.githubusercontent.com/git202526/xau-desk-data/main/data.json";
```

- 优点：打开即最新，raw CDN 缓存约 5 分钟，链路最短；
- 缺点：实盘仓位对公网可见。用户此前表示「实盘上云也没事，别人以为是模拟数据」，如接受可直接切换；
- 切换成本：`src/config.js` 增加 `dataDirectUrl`，`loadA` 优先直连、失败回退 Actions 快照。

## 6. 取舍结论

| 场景 | 方案 | 状态 |
|---|---|---|
| 改善时效、不碰隐私、不引入外部服务 | **自调度链（本方案）** | **已实施（v2.5.0）** |
| 想彻底脱离 GitHub Actions 调度 | 外部 cron 触发 `workflow_dispatch` | 备选，需细粒度令牌 |
| 追求秒级、可接受公开原始流水 | 方案 B（老应用仓库转公开 + 前端直连） | 未采用 |
| 完全不想改 | `schedule` + 阈值分级 | 已废弃（实测 4–8 小时延迟） |

无论哪种方案，前端都继续显示「源数据 X 前 / 账户快照 X 前」，让用户对数据时效有明确预期，而不是给出「实时」的错觉。

## 7. 另外两条时效陷阱（v2.5.2）

账户链路修好之后，页面还有两处「看起来是刷新问题、实际是口径问题」的地方被用户直接点名，一并记录。

### 7.1 金价：源不同，价格就不同

| 源 | 实测（2026-11-13 同时刻） | 问题 |
|---|---|---|
| `api.gold-api.com/price/XAU` | 3885.77 / 3884.17 / 3889.72（连续三次） | 比新浪高 3.2~8.6，且每次跳；曾报 3909 而新浪约 3880 |
| `hq.sinajs.cn/list=hf_XAU` | 3880.18 / 3880.98 / 3881.13 | 与 XAU Desk 等行情软件逐项对得上 |

**结论**：金价不是「越实时的源越准」，而是「要跟用户对照的那个软件同源」。现改由 Actions 抓 `hf_XAU` 写快照，前端只读；`hq.sinajs.cn` 不返回 CORS 头，前端本来也直连不了。

### 7.2 宏观：日频源永远追不上「今天」

| 源 | 更新方式 | 11-13 能看到的最新值 |
|---|---|---|
| FRED `DGS10` | 日频，T+1 发布，遇美股假期再顺延 | 11-10（11-11 退伍军人节休市） |
| CBOE `VIX_History.csv` | 每交易日收盘后 | 11-12 收盘 |
| **CNBC `US10Y` / `.DXY` / `.VIX`** | 实时，带 `last_time` | **11-13 09:09 EST（当下）** |

页面现在会显示 `数据 22:09 · 3 分钟前`；超过 60 分钟标「源滞后」；一旦回退到日频源，直接写「数据日期 2026-11-10 · 源为日频，非实时」，不再让用户以为它坏了。

> 踩坑：CNBC 多标的必须用 `|`（`%7C`）分隔。用逗号会返回 `{"symbol":"US10Y,.DXY,.VIX","code":"1"}` 的空壳，三项全部落空并静默回退日频源。

## 8. 金价 15 秒实时通道（v2.6.0）

### 8.1 为什么 10 分钟对金价不够

账户数据 10 分钟一档是可以的（人不会每 10 分钟改一次仓位），宏观 10 分钟也够（10Y / DXY / VIX 本身是分钟级慢变量）。但黄金在 10 分钟里走 5~20 美元很常见，用户盯着数字不动，只会得出「卡住」的结论。

### 8.2 选源：CORS × 口径 × 刷新率

| 候选 | CORS | 口径（2026-11-13 23:12 同时刻） | 结论 |
|---|---|---|---|
| `hq.sinajs.cn/list=hf_XAU` | 无（403） | 3882.48，与行情软件一致 | 只能服务端抓，做不到秒级 |
| `api.gold-api.com/price/XAU` | `*` | 3891.87，高约 3 美元且跳动 | 口径漂移，已弃用 |
| `data-asg.goldprice.org/dbXRates/USD` | 403 | — | 不可用 |
| **`qt.gtimg.cn/q=hf_XAU`** | **`*`** | **3893.54；高 3922.99 / 低 3872.91 / 昨收 3877.43 与新浪逐字段一致** | **采用** |

刷新率实测：12 秒采样 7 次，价格在 23:13:56（3893.48）与 23:14:08（3891.51）之间已经变化，而源时间戳只精确到分钟。说明底层快于 15 秒，15 秒轮询能拿到新价。

### 8.3 实现要点

| 项 | 做法 | 原因 |
|---|---|---|
| 抓取 | 浏览器直连 `qt.gtimg.cn`，`arrayBuffer` + `TextDecoder("gbk")` | 响应是 GBK；`Response.text()` 恒按 UTF-8 解，中文名会乱码 |
| 节拍 | 15 秒，`AbortController` 5 秒超时，busy 防重叠 | 一次挂死不能把整条节拍拖垮 |
| 更新范围 | 只改 4 个叶子节点：现价 / 涨跌幅 / 时效 / 晨报数字 | 15 秒重算 buildState 会让决策卡与 FOMO 弹窗抖动 |
| 有效期 | tick 保留 120 秒，超时不再覆盖快照 | 挂后台回来不能看到僵尸价 |
| 隐藏页 | `visibilityState !== "visible"` 直接不发请求 | 省流量、省电 |
| 首屏 | 先 `Promise.race([tick, 900ms])` 再装配 | 否则首屏要干等 15 秒，且会拿旧快照误判「僵尸」 |

### 8.4 三级降级

1. **tick 正常** → `实时 · HH:MM:SS 更新`（每次 tick 时刻都会变，肉眼可确认在跳）。
2. **tick 断掉** → 整页 60 秒刷新自然回退快照价，标 `快照 · 10 分钟同步`，不冒充实时。
3. **连续 3 个节拍（45 秒）没回来** → 标 `实时停顿 · 已 N 秒未更新`。

> 「x 秒前」这种相对时间在本页是无效表达：渲染时刻就是 tick 时刻，永远 0 秒。所以显示的是更新时刻，不是相对时长。

## 9. 档位口径：以老应用为准（v2.7.0）

### 9.1 为什么档位不能「自己算」

老应用的档位价不是一条公式，而是三步：

1. **锚点**：第 1 档 = `H × (1 − 起始跌幅/100)`，`H` 是手动高点（本例 4696）。
2. **档距**：三选一
   - `α×ATR`：`d = α × ATR14`（本例 1.16 × 90.5 = 105）
   - `目标均价`：`d = (p1 − T_eff) / frontCenter(w, k)`，`T_eff` 是「已持仓折算后的目标」
   - `区间`：`d = (终止 − 起始)/100 × H / (n − 1)`
3. **夹取**：`capD = (终止−起始)/100 × H/(n−1)`，`d > capD` 才压到 `capD`（**只压不拉**，未越界时一个字节不改）。

旧实现只做了第 3 步（区间），把第 1 步的起点也当成均分点，于是同一份配置算出档距 190.7，第 5 档 3275.9 —— 而老应用是 3618.59。

### 9.2 每档克重的三个扣减

```
可分配预算 = TOTAL − Σ(未标记档位的买入克重)     ← 已标档的持仓由该档 bought 自然扣
每档计划   = 预算 × w_i / Σw
配额下沉   = 跌破档（现价 ≤ 档位价×0.99）的「待补」按权重挪给未失效档，Σ 守恒
每档待补   = max(0, 计划 − 已补)，已补 = gearMarks[i].g − .sold
```

实测：TOTAL 400、未标档 328.8848 克 → 预算 71.1152 克；权重 5/5/30/50/10/0；现价 3874.69 时第 1、2 档跌破 → 池子 7.1115 克按 30:50:10 下沉 → 23.7051 / 39.5084 / 7.9017 克，与老应用显示逐个数字都对得上。

### 9.3 ATR 必须同源

档距 = α × ATR，ATR 换一条日线，整列档位价就漂。实测同一时刻：

| 序列 | ATR14 | α=1.16 时档距 | 第 5 档 |
|---|---|---|---|
| 老应用 `xau/klines.json`（dukascopy 1d） | 90.51 | 105.0 | 3618.59 |
| 本仓新浪日线 | 91.05 | 105.6 | 3616.1 |

所以 `sync-xau.mjs` 优先抓老应用那份日线算 ATR14 写进快照的 `deskAtr`，前端 `sourceB` 优先读它，缺失才回退本仓日线。残余差异只来自「ATR 会随当日未收盘 K 变动」，量级 0.03%。

### 9.4 交互：每档可点

六个档位都是 `<button data-lv="n" aria-expanded>`，点开看该档计划 / 已补·待补 / 金额（¥ 与 $）/ 距现价 / 触发价（$ 与 ¥ 克）。只重画 M4，不走整页刷新——点一下档位就重拉四个源会闪屏，还会重复触发 FOMO 弹窗。

## 10. 技术面三档条件（v2.8.0）

### 10.1 为什么要把判定拆成条件

熔断条原来只说「偏空 → 暂停买入，等转为中性再恢复」。这句话没错，但**用户没法验证**：不知道中性的门槛、不知道差多少、也不知道数据降级时会怎样。等于给了一个永远兑现不了的承诺。

所以把 `technical.js` 的判定链原样摊开成可以逐条打勾的三组：

| 档位 | 条件（①② 为共用前置） |
|---|---|
| 偏空 | ① 数据链正常 ② 无避险拦截 ③ 得分 ≤ 40 |
| 中性 | ① ② + 得分 41 – 59 |
| 偏多 | ① ② + 得分 ≥ 60 |

### 10.2 判定链的真实顺序

```
① 数据链：B.ok && !stale && indicators.ok   → 不满足即 degraded，dir=0
② 避险：C.mode !== "risk_off"（VIX 单日 >+20%）→ 不满足即 risk_off，dir=0
③ 加权得分 score = 多头权重 /（多头+空头）× 100（四舍五入）
   score ≥ 60 → 偏多 ；score ≤ 40 → 偏空 ；41–59 → 中性
```

前置任一条 ✗ 时 `technical.dir` 恒为 0，三档全部 ✗。这一点在界面上写清楚了，否则用户会误以为「VIX 暴涨 = 中性」。

### 10.3 不准重算第二遍

`core/ladder.js` 只做三件事：读、摊开、算缺口。

- `score` 直接取 `technical.score`（已四舍五入的那个数）
- 档位直接认 `technical.scenario`
- 阈值从 `resolveThresholds(cfg)` 取

任何一处自己重算，都会在下次改阈值时与判定引擎分叉——v2.7.0 的档距漂移（190.7 vs 105）就是「两处各算一遍」的典型案例。

### 10.4 缺口换算

```
delta = 41 − score（score < 41） ；= 59 − score（score > 59） ；= 0（已在中带）
权重缺口 = |delta| × total / 100
```

每 1 个权重单位翻向，得分变化 ≈ `100 / total` 分。所以 `total` 越大（参与投票的指标越多），单个指标翻向越难推动档位。

实例（2026-11-16 14:40 GMT+8）：得分 13 分、`total` 7.86 → 转中性需净 +28 分 ≈ **2.21 个权重单位**，即至少要 2~3 个指标同时翻向才成立。这正是「一根 K 线翻不回来」的量化表达。

### 10.5 视觉语义

| 元素 | 颜色 | 理由 |
|---|---|---|
| ✔ 满足 | 亮金 `#FFC862`（active 档内 `#FFE7B8`） | 表达「条件成立」，是状态不是涨跌 |
| ✗ 不满足 | 灰 `#828C99` | 退后，不与结论抢注意力 |
| 成立档 | 琥珀底 + 边框 + 「成立」 | 与熔断条同色系，形成一条视觉线索 |

不用红绿：这是判断类语义，红绿在本项目里只表示数值涨跌（红涨绿跌）。

## 11. 首页分层结论与技术面增强（v2.9.0）

### 11.1 问题：一句话结论承载不了决策

v2.8.0 之前的 M0 只有一句「晚上好。伦敦金现 X $/oz，RSI14 Y；宏观方向分歧。外部指标同向偏空，减少逆势补仓。」
它把「是什么、为什么、接下来会怎样、什么情况算我错了」压进一句话，读者只能得到方向标签，拿不到任何可核对的东西；M2 也只有 10 个数字格子 + 一句总结。

### 11.2 调研：机构研究稿的五段式

| 来源 | 结论 |
|---|---|
| ChartGuru《XAU/USD Technical Analysis Guide》 | 分析顺序是 regime → key levels → momentum → catalysts → **invalidation**；明确把「单指标当完整决策」列为最常见错误 |
| Cortex Next《Gold Outlook》 | 专业做法是「从预测转向情景规划」：不问「会不会涨」，而问「如果 A 发生，结构指向哪里；如果 B 发生，计划是什么」 |
| TradingView《Expected Move Cone》 | 用 σ₁ 与 horizon 生成前向区间；ATR% 换算 σ 用 `√(π/8)`（正态下 E[range] ≈ σ√(8/π)）；并明确「概率是模型值，不是保证」 |
| World Gold Council《Technical difficulties》 | 关键位用「均线偏离 + 周线 RSI + 波动率峰值 + 回撤位」四件套定位，并给出**失效**（长期动量卖出信号未出现 → 回调不改趋势） |

据此把首页重构为：**定调 → 多周期趋势 → 四层依据 → 波动区间 → 三情景 → 失效条件**，技术面卡片补 **价格位置尺 + 因子贡献 + RSI 刻度**。

### 11.3 口径（`src/core/outlook.js`）

| 项 | 公式 | 说明 |
|---|---|---|
| σ₁ | 最近 20 个收盘对数收益的**总体**标准差 | 不除 n−1；不足 21 根收盘时回退下一行 |
| σ₁（兜底） | `ATR14 × √(π/8) ÷ P` | 区间型波动率 → 标准差的近似换算 |
| σ₅ | `σ₁ × √5` | 5 个交易日 |
| 区间 | `P × exp(±kσ₅)`，k=1 / 2 | 内带 68%、外带 95%（正态基准） |
| 漂移 | `d = clamp((score − 50)/100, −0.5, 0.5)` | 得分只调中位落点，最多 ±0.5σ₅ |
| 情景概率 | `p↓ = Φ(−0.5 − d)`、`p↑ = Φ(−0.5 + d)`、`p↔ = 1 − p↓ − p↑` | 三段和为 1；d=0 时上下严格对称 |
| 情景落点 | `P × exp(dσ₅ ± σ₅)` | 该段的**条件均值**，不是「目标价」 |

`d` 的系数 1/100 是保守取值：得分从 0 到 100，5 日后的中位落点最多偏移半个 σ₅。写死这个上限，是为了让「极端得分」也不会推出夸张的价差；代价是极端行情下模型偏钝，页面因此**同时**展示纯波动的 1σ / 2σ 带，读者可以自己判断哪一侧更可信。

### 11.4 为什么用分层聚合而不是再算一遍

`technical.js` 给每一票打上 `layer`（trend / momentum / band / ext）与 `contrib = dir × weight`，`outlook.js` 只做加总：

```
层净票 = Σ(dir × weight)     共 4 层：趋势(MA20 偏离+均线排列) / 动能(日内+RSI+MACD) / 通道(布林 %B) / 外部(评级+宏观)
```

**绝不按 score 反推层方向**——那是一份数据两套口径的老坑（v2.7.0 档距漂移就是这么来的）。测试 `O8` 专门喂了一组「score=99 但信号全空」的自相矛盾输入，验证聚合仍只认 `dir × weight`。

### 11.5 关键位与失效条件

- 关键位候选：MA5/10/20/50、布林上下轨、20 日收盘高/低；贴线（±0.05%）的位剔除，同价位（0.15% 内）去重，每侧只留最近 2 条。
- 失效条件三件套：得分回中带（41 / 59，与 M4 同源）、收盘站上/跌破 MA5、MACD 柱变号。每条带「未触发 / 已触发」，不给模糊表述。
- MA5 已在现价错误一侧时（暴跌未收复），自动回落到最近的阻力/支撑位，避免写出一条「已经成立」的失效条件。

### 11.6 视觉语义

| 元素 | 颜色 | 理由 |
|---|---|---|
| 四层条 正向 | 琥珀 | 判断类，不用红绿 |
| 四层条 负向 | 靛蓝 | 同上 |
| 区间带 | 靛蓝 10% / 26% 两级 | 表达概率密度，不表达涨跌 |
| 情景「下探 / 反抽」 | 靛蓝 / 琥珀 | 与全站方向色一致 |
| 现价针 | 金色 | 唯一锚点 |
| RSI 30 以下 / 70 以上 | 靛蓝 / 琥珀 | 超卖 / 超买是状态，不是涨跌 |

红绿在本项目只表示**数值涨跌**（红涨绿跌），结论类一律不用，避免把「偏空」读成「绿色=安全」。
